# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

NESTrisChamps is a browser-based capture, broadcast, and rendering system for NES classic Tetris (and Das Trainer). A capture page ("producer") OCRs game state from video and streams it over WebSocket to a Node/Express server, which rebroadcasts it to one or more "renderer" pages (HTML+CSS+JS layouts meant to be used as OBS Browser Sources). Multiple players' streams can be combined into a live head-to-head competition UI with score differentials, tetris rate, pace, etc.

It's a plain ESM Node.js app (`"type": "module"` in package.json) with server-rendered EJS views for a few admin/settings pages, and hand-written vanilla JS for the actual capture/render frontends under `public/`. No frontend build step/bundler is used.

This fork (`drmariotrischamps`, forked from `nestrischamps/nestrischamps`) is adding equivalent OCR support for NES Dr. Mario. The OCR/event layer is self-contained under `public/producer/drmario/` (see below). Versus, "non-networked" single-player, and the "Speed" competitive format (two independent single-player games racing to clear a level set — a lightweight, differently-shaped equivalent of Tetris's `MatchRoom`, not a clone of it) are all wired into the real capture/broadcast pipeline (routing, domain objects, a producer page, an admin page, view layouts — see "Versus pipeline integration" and "Speed pipeline integration" below); there's no DB persistence for any mode yet.

## Commands

- `npm start` — runs the server (`node -r dotenv/config server.js`), reads config from `.env`
- `npm test` — runs Jest (`tests/*.test.js`), using native ESM (no transpilation: `transform: {}` in jest.config.js)
  - Run a single test file: `node --experimental-vm-modules node_modules/jest/bin/jest.js tests/ScoreService.test.js`
  - Run by name: add `-t "pattern"`
- `npm run lint` — runs both `lint-be` (ESLint on everything except `public/`) and `lint-fe` (ESLint on `public/`); backend and frontend have different global/env configs in `eslint.config.mjs`
- Prettier runs automatically on staged files via a Husky `pre-commit` hook (`pretty-quick --staged`) — formatting (tabs, single quotes, semicolons) is enforced at commit time, not just CI
- `npm run session` — utility script to set local session ids for dev/testing
- Local Postgres DB: apply `setup/db.sql`, plus any dated migration files in `setup/` in chronological order (e.g. `20250630.sql`) for schema changes not yet folded into `db.sql`
- Docker: `docker/build.sh` then `docker/run.sh` (docker-compose) spins up the app + a local Postgres container; see `docker/docker-compose.yml` for expected env vars

Required `.env` vars for local dev: `DATABASE_URL` (Postgres connection URI) and optionally `FF_SAVE_GAME_FRAMES=1` (persists captured game frames to `./games/` for replay/analysis). Full config schema (all env vars, including Twitch/Discord/Google OAuth, S3 game-frame storage, TURN server) lives in `modules/config.js` (uses `convict`) — that file is the source of truth for every env var the app reads.

## Architecture

### Two runtime halves

1. **Server** (`server.js`, `modules/`, `routes/`, `domains/`, `daos/`): Express app + a raw `ws` WebSocketServer sharing one HTTP(S) server. Express handles auth/OAuth, REST APIs, and EJS admin pages. The WebSocket server is the real-time backbone — game frames and control messages flow entirely over WS, not HTTP.
2. **Frontend** (`public/`, `views/`, `local_views/`): No build tooling — plain JS modules loaded directly by the browser and EJS-rendered HTML shells. `public/views/1p/` and `public/views/mp/` hold single-player and multiplayer *layouts* (each is a rendering skin: HTML/CSS/JS triplet meant to be dropped into OBS as a Browser Source at 720p). `modules/layouts.js` scans these directories at startup via `glob` to build the list of available layouts — adding a new layout is a filesystem convention, not a registration call.

### Connection routing is all in `routes/websocket.js`

Every WebSocket upgrade is manually dispatched by regex-matching `request.url` (there is no per-route handler abstraction like Express routes). Categories, in the order they're checked:
- `/ws/replay/<ids>` — replays stored games, no session needed
- `/ws/view/<layout>/<user_secret>` — a renderer/layout connecting as a *view*; resolves the owning user via `UserDAO.getUserBySecret` and fabricates a session
- `/ws/room/(u/<login>/)?(producer[12]?|emu)/<secret>` — a capture page connecting as a *producer*, optionally as a producer *into someone else's room* (competition/match mode) when the `u/<login>/` prefix is present
- `/ws/room/admin/<secret>` — the match-room admin control panel (blocked on public server unless routed through session-based auth)
- Anything else requires an established Express session (`request.session.user`)

Read this file first when touching anything connection-related; the in-memory domain objects below assume connections arrive already classified this way.

### Server-side domain model (`domains/`) — all in-memory, no per-connection persistence

- **`User`** (`domains/User.js`): one instance per logged-in user, kept alive in memory while it has active connections (auto-expires 30 min after last connection closes — see `checkScheduleDestroy`). Owns a `Producer`, a `PrivateRoom`, and a `MatchRoom`, and optionally joins another user's `MatchRoom` for head-to-head play. Also owns the optional Twitch chat client (`@twurple`) relaying chat/sub/raid events to connected clients.
- **`Producer`** (`domains/Producer.js`): wraps the capture-page WebSocket connection for a user. Parses incoming binary game frames vs JSON control messages, and owns the current `Game` instance (`modules/Game.js`), recreating it whenever a new game start is detected in the frame stream.
- **`Room`** (`domains/Room.js`, base class) / **`PrivateRoom`** / **`MatchRoom`**: fan out producer messages to connected view (renderer) connections. `MatchRoom` is the interesting one — it models up to `MAX_PLAYERS` (16) player slots, an admin control connection, auto-join logic, best-of-N/victories tracking, and a large command switch (`handleAdminMessage`) that is the actual protocol for the match-room admin UI.
- **`Connection`** (`modules/Connection.js`): thin `EventEmitter` wrapper around a raw `ws` socket — handles ping/pong keepalive, binary-vs-JSON message decoding (binary always means a game frame, decoded via `public/js/BinaryFrame.js`), and a "kick" sequence (send `_kick`, close, then hard-destroy after a delay so the client has time to see the message).

### Wire protocol

- **Control messages**: JSON arrays, `[command, ...args]`, sent as plain WS text frames. Most of the domain classes' message handling is just switching on `message[0]`.
- **Game frames**: a fixed 74-byte binary format (see `docs/schema.md` for the full byte layout) encoded/decoded by `public/js/BinaryFrame.js`, shared verbatim between server and browser code (this is why `jest.config.js` maps `/js/*` and `/views/*` to `public/js`/`public/views` — tests import the same frontend modules the browser loads).
- Score/stat computation from raw frames happens both client-side (live rendering, in `public/views/*.js`) and server-side (persisted scores via `modules/Game.js` → `daos/ScoreDAO.js` → Postgres `scores` table).

### Data layer

- `modules/db.js` exports a single shared `pg.Pool`, configured from `DATABASE_URL`.
- `daos/` (`UserDAO`, `ScoreDAO`) are the only modules that issue SQL directly — raw parameterized queries, no ORM.
- `domains/ScoreService.js` sits above `ScoreDAO` for query-option parsing/validation (allowed sort fields/dirs, page size clamped to `server.max_page`, competition-flag filtering) — extend validation there rather than in routes or the DAO.
- Schema evolves via dated one-off SQL files in `setup/` (e.g. `20250630.sql`) rather than a migration framework; `setup/db.sql` is the baseline.

### Config

All environment variables are declared and validated centrally in `modules/config.js` via `convict` (with a custom `boolean-string` format for env vars like `"true"`/`"1"`). `config.validate({ allowed: 'strict' })` runs at import time, so an unrecognized/undeclared env var will crash startup — always add new env vars to this schema rather than reading `process.env` directly elsewhere.

## Dr. Mario OCR (`public/producer/drmario/`)

A from-scratch OCR system for NES Dr. Mario, built the same way the Tetris OCR was originally derived: by pixel-analyzing real captures rather than guessing geometry/colors. Status: piece/panel identification is implemented and tested for both single-player and versus mode, and both are wired all the way into the real capture/broadcast pipeline (see "Versus pipeline integration" below — the name predates single-player joining it, but the same integration covers both). `tests/fixtures/dr_mario/*.png` are the real captures everything below was derived from and is tested against — add new ones there (with matching new Jest assertions) rather than hand-editing templates when new game states need covering.

**Key design difference from the Tetris OCR**: Tetris reads a field cell as one flat color sampled against a level palette (`../cpuTetrisOCR.js`'s `scanField()`), because a Tetris block always renders identically regardless of piece type. Dr. Mario can't do that — a virus and a pill segment can be the exact same color — so cells are identified by matching the actual NES tile *shape* (a small bank of hand-derived lit/unlit pixel templates), with color as a secondary signal. See `templates.js` for the full reasoning and how virus color/animation-frame and pill shape/color decompose differently (virus shape implies color; pill shape is color-independent, color needs separate sampling).

**Module map**:
- `shapeMatch.js` — shared pixel-sampling/template-matching primitives (`sampleRegion`, `trimToContent`, `matchBestTemplate`), used by every reader below. `sampleRegion`'s `invert` flag matters: sprites-on-black use bright-is-lit, but the score panel is black-text-on-light and needs the opposite — getting this backwards silently produces garbage matches (happened once; see git history on `PanelOCR.js`).
- `templates.js` / `digitTemplates.js` / `crownTemplates.js` — the actual shape banks (virus/pill tiles, the digit font + SPEED word, the versus-mode crown icon), each with real per-pixel provenance documented inline.
- `spriteBitmaps.js` / `CellRenderer.js` — real full-color NES sprite art for bottle rendering (see the `drmario_*_nes.html` layouts below), a separate concern from `templates.js`'s lit/unlit OCR-matching silhouettes even though both are derived from the same fixture captures. `spriteBitmaps.js` is generated data (a one-off extraction script, not committed, same precedent as `resultTemplates.js`): it ran the already-tested `BoardOCR.identifyCell()` classifier across several clean emulator fixtures and sampled the raw 8x8 RGB pixel grid of every cell it confidently identified, rather than hand-transcribing anything — see its own header comment for exactly which fixtures and the full provenance/gap accounting. 10 of the 15 (pill shape, color) combinations were found directly; blue left/right were *also* found directly but deliberately discarded and composed instead (see below), so 6 total are composed (documented per-entry) by taking a same-shape instance in a different color and substituting tones, since pill shape is confirmed color-independent (`templates.js`) and each pill color empirically turned out to use exactly 2 fill tones (its own `COLOR_PALETTE` base plus one shared "highlight" tone). The blue left/right discard: both were auto-found in `level00_frameA.png` (a *falling*-piece capture, unlike every other directly-sampled shape, which came from the landed `level00_pill_shapes.png`), and that particular instance rendered 1px lower than the canonical landed alignment — confirmed both by direct pixel inspection and live, after wiring this in, by the user (visibly offset from every other pill on screen) — exactly the per-instance jitter `templates.js`'s own header comment already warns about. Composing both halves from red's canonical pattern instead (not just the one side initially reported) keeps the pill's two halves aligned with *each other*, not only with the rest of the board. `CellRenderer.js` turns the bitmaps into cached offscreen canvases once at load and exposes `drawCell(ctx, x, y, size, cell, virusFrame)` (nearest-neighbor `drawImage` scaling, no per-pixel loop on redraw) and `currentVirusFrame(intervalMs = 125)` — a flat wall-clock toggle, deliberately *not* the `frame` value `identifyCell()`/`scanBoard()` already report per virus cell live. Using the real OCR-reported frame was considered and rejected directly with the user: it would risk visible flicker under real capture jitter (see `hasBottle`'s own jitter-tolerance fix) and would let different viruses in the same bottle drift out of sync with each other (each cell's own independent OCR read), whereas one shared clock keeps every virus blinking in unison — arguably more authentic to the real game (all its viruses animate on one shared beat) even though it isn't synced to any particular capture's real timing. Doubled twice from an initial 500ms guess (500 → 250 → 125ms), per direct feedback each time that it still read as too slow — none of these figures is a measured NES timing value (none exists in this codebase), purely cosmetic.
- `BoardOCR.js` — `identifyCell()`/`scanBoard()` (the 8x16 bottle grid) and `identifyNextPill()` (the preview pill, positioned above Mario's head in single-player or in each bottle's neck in versus — a fixed screen position, not a grid cell). Both take a `field`/`position` option so the same code drives either single-player's one bottle or versus mode's two. `identifyTile()`'s `DEFAULT_MAX_DISTANCE` (max acceptable shape-template mismatch count before falling back to `type: 'unknown'`) was raised from an initial 6 to 12 after a real remote/Twitch-relayed single-player capture — confirmed correctly calibrated first (the bottle's own cyan walls, pixel-measured directly off a producer.html screenshot, landed within 1 reference pixel of `constants.js`'s `FIELD`) — still showed widespread `'unknown'` cells, concentrated in recently-active regions of the board (a fresh spawn, a piece mid-fall) rather than long-settled ones near the bottom, consistent with video compression allocating fewer bits to fast-changing content than to static, already-converged regions. Raising the accept threshold doesn't change *which* template wins (still whichever scores lowest), only whether a genuinely-closest-but-imperfect match gets trusted instead of rejected — a live-tuned value, not a measured one, like several other pragmatic constants in this module family (e.g. the SALT-per-row figure, the virus blink interval).
- `PanelOCR.js` — `readNumber()` (TOP/SCORE/LEVEL/VIRUS digit sequences) and `readSpeed()` (LOW/MED/HI, matched as a whole word, not per-letter). `DEFAULT_MAX_DISTANCE` raised from an initial 3 to 6 alongside BoardOCR's own increase, for the same compression-noise reason — the same remote-capture test above showed every single panel field failing (`readNumber()` requires *every* digit in a field to match confidently, so a 7-digit field like TOP/SCORE compounds each digit's own noise-driven failure risk multiplicatively, making a small per-digit tolerance bump matter more here than it would for a single-shape board-cell read). Both are now thin wrappers around debug variants — `readNumberDebug()` returns one `{value, distance, bestGuess}` per digit slot (`digitsToValue()` collapses that array to `readNumber()`'s plain number-or-null, returning `null` the instant any slot's `value` is `null` rather than assembling a number from rejected guesses) and `readSpeedDebug()` returns the same single-object shape for the whole word; `readNumber()`/`readSpeed()` themselves keep an unchanged public contract, just implemented in terms of these. Added specifically so the calibration UI's per-region diagnostics (see "Independent per-region calibration" below) can show *why* a field isn't reading — a raw distance number and the closest template it almost matched — rather than just a blank/wrong value, requested directly after a remote capture debugging session ended before VIRUS/SPEED could be fully diagnosed live ("let's go ahead and add the diagnostics though so we'll have it for later").
- `CrownOCR.js` — versus-mode round-wins tracker; reports a win *count* per player rather than assuming which grid cell fills first (only one example was ever observed).
- `resultTemplates.js` / `ResultOCR.js` — `readResult(image, field)` reads a bottle's round/match state: `'playing'` | `'stage_clear'` | `'game_over'` | (versus only) `'topout'`. STAGE CLEAR and GAME OVER are the same box design (red border, yellow fill, vertically centered on a fixed point regardless of text length) anchored to each bottle's own position, so one template pair and one bottle-relative sample region covers single-player and both versus bottles; topout is a separate, smaller, lower box sampled at its own offset, since it doesn't replace the bottle's contents (the overflowed pieces stay visible above it) the way the other two do. `resultTemplates.js` is generated by a one-off extraction script, not hand-transcribed — see its top comment before hand-editing it (a manual first attempt silently dropped rows and produced garbage matches). `readResult` assumes a bottle is actually present — see `ScreenOCR.js` below for the screens where that's not true.
- `ScreenOCR.js` — `hasBottle(image, field)`, answering "is there a bottle on screen at all," distinct from (and a prerequisite for trusting) everything else above. Dr. Mario has several screens with no bottle whatsoever — pause (the screen goes black except white "PAUSE" text), the title screen, and the 1P/2P game-setup menu — and every other reader here just produces misleading output if pointed at one instead (an all-black pause screen reads as an empty board; `ResultOCR`'s `'playing'` default makes a title/menu screen look like an ordinary in-progress round). Rather than building a detector per screen, it checks for the cyan bottle-wall color at two fixed points relative to `field`'s own origin — present on every real bottle, absent on all three non-gameplay screens. `isTitleScreen(image)` narrows further, telling the title screen apart from pause/menu specifically (a whole-screen check, no `field`) — needed because a player can soft-reset the console mid-round via a controller command, jumping straight to the title screen with none of the usual `'game_over'`/`'topout'` result on the way (see `RoundTracker.js`). Keys on the title screen's decorative checkerboard, which alternates between two greens — the darker shade alone isn't unique (some ordinary gameplay levels' own checkerboard uses it too), but the brighter one never appears anywhere else on hand.
- `constants.js` — all geometry (`FIELD`, `NEXT_PILL`, `VERSUS.*`), the `COLOR_PALETTE`, and `LAYOUT`/`CONFIGS`/`REFERENCE_LOCATIONS`(`_VERSUS`) tying it together. Every coordinate here was measured off a real capture, not estimated — see the git history for the actual pixel-dump methodology if new geometry ever needs deriving (e.g. for a layout variant).
- `DrMarioOCR.js` — the DOM-facing live-video counterpart to the above (mirrors `../TetrisOCR.js`'s shape: `EventTarget`, `processVideoFrame({video, videoFrame})`, a `'frame'` event). Versus mode (unchanged, deferred) still uses one axis-aligned crop rectangle (video pixels → the 256x224 reference frame) — no skew/rotation correction. Single-player instead captures each of `constants.js`'s `CALIBRATION_REGIONS` independently — see "Independent per-region calibration" below for the full story of why and how. Every scanned bottle is gated through `ScreenOCR.hasBottle` first: when it's false the returned per-bottle shape has `hasBottle: false` and every other field (`result`/`board`/`nextPill`/`level`/`virus`/`speed`, plus `top`/`score` in single-player) null, rather than running the rest of the OCR pipeline against a screen it wasn't built to read. `isTitleScreen` (from `ScreenOCR.isTitleScreen`, computed once per frame against a whole-screen capture that both layouts still take) is attached to every per-bottle shape the same way `hasBottle` is, even though it's a whole-screen fact rather than a per-bottle one — `RoundTracker` only ever sees one bottle's frames, so it needs the flag on its own frame object to act on it.
- `RoundTracker.js` — the per-bottle state machine (mirrors `../GameTracker.js`'s role) that turns a *sequence* of frames into `round_start`/`round_level_confirmed`/`round_ready`/`round_end`/`piece_entered`/`garbage_entered`/`virus_cleared` events. One instance per bottle (versus mode uses two). Unlike GameTracker it doesn't need a score/lines heuristic to find round boundaries — `ResultOCR`'s state already gives that directly — and it tracks virus count as two-phase (up during population toward `4*(level+1)`, capped at 84 for level 21+, then down) rather than monotonic. `piece_entered` fires when a player-controlled piece spawns, detected by position and scoped specifically to the fixed pair of middle columns a real spawn always uses (confirmed report), *not* the whole top row — an earlier version watched the whole row and misread the player shifting/rotating a piece still sitting in row 0 as repeated new spawns. Scoping to the spawn pair alone still double-counted real player input (a piece slid off the spawn pair and back, or rotated 180° in place, both leave then re-fill it without a real spawn happening — confirmed live), so re-arming detection now requires positive evidence the previously-reported piece actually left play: either the next-pill preview changing (confirmed via real captures — see `BoardOCR.identifyNextPill`'s doc comment — to hold constant while the current piece is in play; blind spot: two real consecutive pieces can coincidentally share a color pair, since there are only 3 colors) or new pill content appearing one row below spawn or deeper (a rotation alone can never reach that far — confirmed report that the second cell of a vertical pill goes *up*, off the top of the bottle, not down; blind spot: a piece that locks against a tall stack before ever falling that far). The two blind spots are unrelated, so either signal alone is enough to disambiguate; only their conjunction still double-counts (documented and tested, not fixed). `piece_entered` also requires both spawn cells to be the paired `'left'`/`'right'` shapes specifically (not just any pill), so a garbage half (see below) landing on a spawn column can never be misread as part of a real spawn. `garbage_entered` (versus only) fires when one or more loose `'single'`-shaped halves (see `templates.js`'s `PILL_SHAPE_TEMPLATES`) appear on the top row — confirmed report: 2/3/4 can enter at once, always with at least a column of gap between them, landing in any column including the spawn pair — batched into one event per frame per column that was genuinely empty the frame before; a `'single'` overwriting an already-occupied column is deliberately not tracked (confirmed report that garbage does this, but not a case worth the complexity of reporting precisely). Detection stays disarmed at the start of each round until a frame where the *entire* top row reads empty has actually been observed (`#topRowConfirmedEmpty`) — `#topRowEmpty` otherwise resets to an optimistic all-empty default on every `#startRound()` with no real prior-frame observation behind it, and a half-pill orphaned by a match clear late in the *previous* round can still be visually sitting in the top row for the first frame or two of the next one, before the screen actually clears it; without this guard that leftover cell reads as a same-frame empty-to-single transition and fires a false `garbage_entered` before the player's first piece has even spawned (reported live). Each cell also carries `restRows` — how many rows it'll fall before resting, inclusive of the spawn row, computed once at arrival from the board already in hand rather than tracked live as it actually falls (garbage falls at a constant rate regardless of game speed, so both approaches land on the same number) — plus `maxRestRows` on the event as a whole (the farthest-falling cell in the wave); purely geometric, exists for `LiveMetrics.js`'s SALT stat, not used by round-lifecycle logic itself. `virus_cleared` fires whenever the tracked virus count drops during ordinary play (population increases don't count, handled separately), with the delta so a poll that misses an intermediate frame still attributes the right total — also purely for `LiveMetrics.js`'s benefit. `pill_thrown` fires on a readable-to-blank transition of the next-pill preview, added after a direct report that it reliably goes blank for a few frames during the real game's own pill-throw animation, once per piece — a simpler, more direct signal for `LiveMetrics.js`'s pieces/minute pace stat than `piece_entered`'s own spawn-pair-occupancy detection, which is unchanged and still what rush-streak/color-drought/`InternalSpeed`'s own piece count key off (this new event carries no cell/color data to feed them). `#nextPillBlank` starts each round `null` (not yet observed), not `false` — the very first frame processed after a round starts only ever seeds the baseline and never fires, regardless of whether it happens to read as blank (e.g. `nextPill: null` before calibration, or simply because no frame has been read yet); without that distinction a round whose first processed frame has no readable next-pill data would register a spurious "into blank" transition before any real piece has spawned. Tradeoff: if a round's very first processed frame already happens to catch its first piece mid-throw, that first piece is undercounted by one — an acceptable rounding error for a per-minute rate averaged over a whole run, and safer than risking a spurious over-count on every round's first frame. A frame with `hasBottle: false` (see `ScreenOCR.js`) is a complete no-op *unless* `isTitleScreen` is also true and a round was actually in progress — a soft reset via a controller command jumps straight to the title screen mid-round with no `result` transition to detect otherwise, which would leave a round stuck open forever without this; ordinary pause/menu screens still don't look like a round boundary, and a title/menu screen in front of the capture still can't bootstrap a bogus `round_start`. Versus mode's round boundary is shared between both bottles — one player's win/loss ends the round for both, even though the other bottle's own `result` reading can keep showing `'playing'` (reported live) — which a single instance watching only its own bottle can't notice on its own, so `endRound(outcome)` lets the consumer running both players' trackers (see `harness.js`'s versus wiring) propagate one tracker's `round_end` onto the other; it's a no-op if that tracker already ended its own round, so cross-wiring both directions can't double-fire or loop. The same desync happens in reverse at the *start* of the next round (reported live): the unaffected bottle's own board/panel data can already reflect the new round before the affected bottle's own overlay has cleared (that one's `result` only reads `'playing'` again once it does), so letting the unaffected tracker self-detect its own round_start would report the round starting a real amount of time before it actually does for the affected player. A tracker that ended via `endRound()` now waits instead of self-detecting; `syncRoundStart({roundId})` (same versus wiring, on `round_start` this time) relays the affected tracker's own later, real round_start onto it, also a no-op unless that tracker is actually waiting for one. Deliberately takes only `roundId`, never `level` — each player's level is set independently (reported live: 1P on level 7 while 2P was on level 0), so borrowing it from the other tracker was a real regression caught live (round_ready firing far too early off the wrong target); the synced round starts with `level: null` and lets it self-heal from this bottle's own frames exactly like an ordinary unreadable-at-round_start case. Pure state-machine logic, no OCR/pixels involved — tested against hand-built frame sequences, not image fixtures; this particular heuristic hasn't been validated against real captured timing data, only against live-harness repros.
- `LiveMetrics.js` — a live-stats layer built on top of one `RoundTracker`'s events, mirroring how Tetris's `../views/BaseGame.js` (simple running counters off discrete events) sits under `../views/Player.js`/view-layer closures (bespoke streaks) rather than any of it living in the frame-decoding layer itself — researched that split deliberately before designing this. Named `LiveMetrics`, not the more obvious "StatsTracker" — that name shipped first and was found live to trip ad/tracker-blocker extensions (`ERR_BLOCKED_BY_CLIENT`) that filter requests matching generic "stats"/"tracker" analytics-script patterns, silently killing the whole page's script execution (the sibling `RoundTracker.js`, no "stats" in its name, loaded fine) — renamed rather than asking every viewer to allowlist the domain. One instance per bottle, `EventTarget`-based like `RoundTracker`, dispatches one `stats_updated` event (a full snapshot via `getSnapshot()`) on any change. Self-derived from its own bottle: `piecesPerMinute` (increments off `RoundTracker`'s `pill_thrown` event, not `piece_entered` — see `RoundTracker.js`'s own entry above for why)/`virusClearsPerMinute` (wall-clock `Date.now()`, no prior time-basis convention existed anywhere in this codebase to match — see `../views/BaseGame.js`'s `duration`/`modules/Game.js`'s `duration` for the two unrelated, non-rate conventions that do exist), `colorDroughts` (per-color pieces-since-last-seen, directly mirrors `BaseGame.js`'s per-piece-type drought), and `rushStreak`/`maxRushStreak`/`isRushing` (3+ *exact same piece including orientation* in a row — order matters, e.g. blue-red/blue-red/red-blue/blue-red is not a rush since the third piece's swapped orientation breaks it, confirmed report) — droughts and rush still key off `piece_entered` specifically (via `#onPieceEntered`), since they need the actual cell/color data `pill_thrown` doesn't carry. Externally reported (versus only): `recordGarbageSent({cellCount, maxRestRows})` — not wired to its own bottle's events at all, since "garbage sent" is inherently about the *other* bottle's `garbage_entered`; the consumer calls it on player A's tracker when player B's `garbage_entered` fires, the same cross-player-coordination-lives-in-the-consumer split `RoundTracker`'s `endRound()`/`syncRoundStart()` already established — feeds `garbageWavesSent` (a plain running total; the versus view displays this and its derived rate as "combos", the term the user actually uses for a wave of garbage), `garbageWavesSentPerMinute`, `averageGarbageWaveSize` (labeled "CUR" — Combo Utilization Rate — in the view; that name and the display threshold below are both view-layer choices, not something `LiveMetrics` itself encodes), and `saltSeconds` (cumulative, `maxRestRows * 0.25`s per call, since garbage falls at a constant rate regardless of game speed — briefly changed to 0.2667 on a correction from the user that turned out to be wrong and reverted back to the original 0.25 figure). The per-row constant is also exported (`SALT_SECONDS_PER_ROW`) so a view can time a display-only "count up" animation against the exact same figure the accumulation itself uses, rather than duplicating it — see `drmario_versus.html` below. Single-player's own round boundary fires on every *level*, not just when a playthrough ends (a `round_end` with `outcome: 'stage_clear'` just advances to a harder level, same playthrough) — resetting the *pace* stats (`piecesPerMinute`/`virusClearsPerMinute`) on every one of those would make them jump every time a level clears, so a `carryAcrossLevels` constructor option (single-player only, off by default) makes `LiveMetrics` listen to `round_end` too and only fully reset on the *next* `round_start` if the previous round didn't end in `'stage_clear'`. Rush streak and color droughts are different, per direct request: those reset fresh on every new level regardless of `carryAcrossLevels`'s own outcome-tracking — they're about *recent* piece patterns, not the whole run's pace, so `#resetLevelStats()` (a level-up within the same run) resets just `colorDroughts`/`rushStreak`/`maxRushStreak`, leaving `piecesCount`/`virusClearsCount`/`runStartTime` untouched, while a genuinely new run still calls the full `#reset()` (which itself calls `#resetLevelStats()` plus the rest). Versus keeps the simpler always-full-reset-per-round default, since it has no "advance to a harder level, same run" concept today (match-wide stats across a best of 3/5 are a possible later expansion, not this). A public `resetRun()` is also exposed as a manual override regardless of automatic detection, wired to a button in both view layouts.
- `InternalSpeed.js` — `calculateInternalSpeed(speedName, piecesEntered)`, a pure/stateless function decoding the game's real internal fall-speed from the displayed LOW/MED/HI value, which isn't the actual speed the game runs at. Per the user's own account of the mechanic: a base value per displayed speed (LOW 15, MED 25, HI 31) increases by 1 as the 9th pill enters a level (i.e. once the 8th has locked), then by 1 again every 10 pills after that, up to a cap of 49 increases (HI caps at 80, MED at 74; LOW's cap of 64 follows the same +49 pattern but wasn't independently confirmed). `piecesEntered` is a running count of `RoundTracker`'s `piece_entered` events since the current round started, tracked inline in each view (not in `RoundTracker`/`LiveMetrics` itself — this is a self-contained, easily unit-tested calculation, not round-lifecycle logic or a rate/streak stat) and reset unconditionally on every `round_start`, regardless of single-player's `carryAcrossLevels` — the real game's own speed ramp genuinely restarts every level, it isn't a "run" concept the way pieces/min is. All 4 view layouts (`drmario_single(_nes).html`, `drmario_versus(_nes).html`) now display this computed number in place of the raw LOW/MED/HI text.
- `SpeedRunTracker.js` — one instance per player, consuming one player's own `RoundTracker` events, for the "Speed" competitive format (see "Speed pipeline integration" below): a wall-clock run timer spanning an admin-configured set of consecutive levels, per-level split times, and `totalVirusesRemaining` (the live remaining virus count on the current level plus the full `virusTarget()` — exported from `RoundTracker.js` for exactly this — for every level in the set not yet reached), which normalizes a "viruses ahead" comparison so it stays meaningful even when the two players are on different levels, replacing an initially-considered same-level-only restriction. Deliberately has no notion of "match," "opponent," or "victories" — that state lives server-side in `DrMarioSpeedRoom.js`, combined with two independent `SpeedRunTracker`s only at the view layer, the same separation `RoundTracker.js`'s own header comment already establishes for cross-player coordination. Per DrMC's own Speed rules the total time is genuinely wall clock from the first level's start to the last level's clear — a topout mid-set doesn't end the run, the player just restarts the level they died on (confirmed directly), so a same-level retry is deliberately a no-op on `runStartTime` and prior splits; the run simply keeps ticking, which is also why no "attempt" segmentation is needed anywhere in this module. Level-start detection listens to both `round_start` and `round_level_confirmed` (not just the latter) — `round_start`'s own `level` is already non-null whenever it was readable on the triggering frame (the common case), and `round_level_confirmed` only fires later for a round that *started* unreadable; missing this the first time silently meant a run would never start whenever the level was already known upfront, caught by the module's own test suite before shipping. Split timing is a deliberate hybrid, per direct instruction to make it precise rather than settle for the simpler `round_end`-only timestamp: a `virus_cleared` delta run against a starting count from `round_ready` marks the exact moment remaining viruses first hits 0, but that timestamp is only *used* once the subsequent `round_end` actually confirms `outcome: 'stage_clear'` on the expected level — so a single garbled OCR frame misreading virus count can't corrupt state, only at worst get self-corrected by the next real frame. `MAX_CLEAR_TIMESTAMP_LAG_MS` (5000ms) guards the other failure direction, reported live on `QualifyRunTracker.js` (which shares this exact mechanism): if something stalls play between the virus-zero crossing and `round_end` actually firing (a pause, a capture/OCR hang), the stashed timestamp can lag the real clear moment by far more than ordinary OCR/animation delay ever would — a live report showed a level's split reading 10s when the real clear took 27s, with the missing 17s then showing up as *already elapsed* time on the next level's own live display (a too-small split directly corrupts `SpeedRunTracker`/`QualifyRunTracker`'s own per-level-elapsed math, which subtracts the previous split from total elapsed). Past that threshold, `#onRoundEnd` falls back to its own `Date.now()` instead of the stale stashed value — less "precise" than the virus-zero-crossing moment in the ordinary case, but never wrong in the direction that corrupts a later level's display. Tested the same way `RoundTracker`/`LiveMetrics` are (`tests/DrMarioSpeedRunTracker.test.js`) — hand-built frame sequences, no OCR/pixels, each tracker instance tested standalone since (unlike Versus's two `RoundTracker`s) the two players' races are never cross-wired.
- `calibrationMath.js` — pure calibration math shared by `producer.js`/`harness.js` (`fieldAnchorForLayout`/`calibrationFromBottleRect`/`bottleRectFromCalibration`/`deriveAllRegionsFromScreen`), deliberately kept DOM-free and extracted into its own module specifically so it has real test coverage (`tests/DrMarioCalibrationMath.test.js`) — `DrMarioOCR.js` itself can't be unit-tested directly (`document.createElement('canvas')` etc, and this project's Jest config runs `testEnvironment: 'node'`, no jsdom), so this is the only piece of the calibration feature below that a test can reach. See "Independent per-region calibration" for what these functions actually do.
- `harness.html` / `harness.js` — standalone page (not part of `ntc-capture`/`CaptureDriver`/the real broadcast flow) for visually testing the above against a real camera or screen/window capture, including a live `RoundTracker` event log. Open `/producer/drmario/harness.html` directly.

**Independent per-region calibration (single-player)**: debugging a real remote (Twitch-relayed) Speed capture surfaced a structural problem, not a one-off calibration error — different remote players' capture setups aren't consistent with each other. Some include 8 rows of NES overscan above/below the visible screen that others don't; at least one player cropped their capture tighter at the bottom to match a template they'd been given independently. The single-calibration-rectangle model every other section on this page assumes (one linear transform, `constants.js`'s `REFERENCE_LOCATIONS`/`FIELD`/`NEXT_PILL` as fixed offsets within it) can't represent a non-uniformly cropped source — there's no one affine transform that gets the bottle *and* the LEVEL/SPEED/VIRUS panel right at once if the true source was cropped differently top vs. bottom. Ported the fix from the existing Tetris OCR in this same codebase, after directly researching its actual implementation (`cpuTetrisOCR.js`/`TASK_RESIZE`), not just inferring from precedent: it captures named regions (field, next box, score, level, etc.) fully independently, each resampled to its own fixed working-canvas size regardless of its own raw source crop's pixel dimensions — that per-region resampling, not just independent positions, is what actually absorbs a given player's own overscan/cropping quirks without requiring every other region to match. Scoped to single-player only for now; versus keeps today's single whole-screen calibration unchanged (~13 regions across 2 bottles + shared panels + a crowns grid — a similarly-sized second effort, not needed for the immediate remote-Speed-capture problem this was solving).
- `constants.js`'s `CALIBRATION_REGIONS` (one entry per `field`/`next_pill`/`top`/`score`/`level`/`virus`/`speed`) holds, per region: `refPoint`/`size` — that region's position/size in the *old* shared 256x224 frame, used only once as the "quick seed" extrapolation anchor (see below), never consulted again at read time — and `local` — the coordinates `BoardOCR`/`PanelOCR`/`ScreenOCR`/`ResultOCR` actually get called with once that region is captured into its own small canvas (mostly `{x:0,y:0,...}`, since most regions need no margin beyond their own tight content). `next_pill`'s `size` deliberately uses `CELL_SIZE * 2` (16px), not `REFERENCE_LOCATIONS.next_pill.crop.w` (15px, informational only there — `identifyNextPill()` ignores it and always steps by `CELL_SIZE`) — 15px would clip the last column of the right-hand tile's own capture. `top`/`score`/`level`/`virus`/`speed`'s `local` nests coordinates under `crop` (rather than flat x/y/w/h like `field`/`next_pill`) specifically because that's the shape `PanelOCR.readNumber()`/`readSpeed()` actually take. `field` alone needs a margin beyond the bare playfield interior: checked every field-relative offset directly against the numbers already in this codebase before deciding this — `ResultOCR.js`'s `RESULT_BOX_OFFSET`/`TOPOUT_OFFSET` are both confirmed to stay entirely within the interior's own 64x128 bounds, but `ScreenOCR.hasBottle()`'s wall-check points reach outside it (~9px left / ~8px right of the interior, from its own `LEFT_WALL_OFFSET`/`RIGHT_WALL_OFFSET_X_PAD`/`WALL_SAMPLE_RADIUS`) — `FIELD_MARGIN` (12 reference px, uniform on all sides) is comfortably generous relative to that measured need, giving `field`'s own captured canvas an 88x152 size with the true interior living at local `(12,12)`.
- `DrMarioOCR.js`'s `processVideoFrame()` does one `drawImage()`/`getImageData()` into the shared whole-screen canvas (as before, for `isTitleScreen()`) *plus*, for single-player, one more independent pair per `CALIBRATION_REGIONS` entry (`#captureRegions()`/`#drawAndSample()`), each scaled from that region's own video-pixel crop into its own persistent small canvas (also exposed via a new `getRegionCanvas(name)`, mirroring `getReferenceCanvas()`). `#scanSinglePlayer()` returns the same "not calibrated yet" no-op shape as before if *any* region is still uncalibrated, now checked per-field instead of all-or-nothing. It also computes each panel field's debug read (`readNumberDebug()`/`readSpeedDebug()`, from `PanelOCR.js` — see above) regardless of `hasBottle`, stashed in `this.last_panel_debug` and exposed via `getLastPanelDebug()`, so the calibration UI can show live distance/bestGuess numbers even on a frame that isn't producing a usable broadcast value; reset to `null` in the "not calibrated yet" branch. Versus's own `#scanVersus()`/`#scanVersusBottle()` are untouched — still reading from the one shared whole-screen image via the plain (non-debug) `readNumber()`/`readSpeed()`, which is why `DrMarioOCR.js` still imports both alongside the new debug functions.
- Calibration UI (`producer.html`/`producer.js`, `harness.html`/`harness.js`, both updated): a "quick seed" click-to-calibrate (whole screen, or the bottle-anchored mode from before — both still just derive one whole-screen rect) now also calls `calibrationMath.js`'s `deriveAllRegionsFromScreen()` to populate a starting value for every region from that same rect, via the same linear-extrapolation math `calibrationFromBottleRect()` already used for the bottle alone, generalized to every `CALIBRATION_REGIONS` entry. Below that, one small box per region — its own live preview (`ocr.getRegionCanvas(name)` appended directly into the DOM, so it just keeps redrawing itself every frame with no extra render code needed, the same trick `getReferenceCanvas()` already used) plus its own X/Y/W/H inputs — lets the operator independently fix up whichever region a non-uniform crop actually threw off, without touching any other region; this directly answers a concrete gap raised live after the bottle-anchored mode shipped ("I don't have a preview of the OCR of just that section"). Editing the whole-screen X/Y/W/H fields directly (as opposed to a fresh click) deliberately only touches the `screen` value, not `regions` — it can't clobber per-region fine-tuning already done; only an explicit new click-to-calibrate re-derives every region from scratch. The region fine-tune section hides itself when the layout selector is set to Versus (`updateSectionVisibility()`), since none of it does anything in that mode. `harness.js` got the same core support and region fine-tune UI, but not the bottle-anchored quick-seed mode specifically (kept that page's own diff smaller; whole-screen quick-seed still works there).
  - The `field` region's preview defaults to cropped to just the true playfield interior (hiding `FIELD_MARGIN`'s extra 12px border on every side) via a "Hide margin" checkbox, checked by default — requested directly ("hard to fine tune with that added border... can we make that an option to see?") since the margin makes it harder to judge by eye whether the interior itself is snugly aligned. `applyFieldPreviewCrop()` toggles between the full post-margin preview (used to confirm the margin itself looks reasonable) and the cropped one by resizing `.region-preview-holder` to `local.w`/`local.h` and negatively offsetting the canvas inside it by `local.x`/`local.y` (both from `CALIBRATION_REGIONS.field`) — the holder's `overflow: hidden` does the actual clipping, the canvas itself is never redrawn or resized. Every other region has no margin to hide, so only `field`'s box gets the checkbox.
  - Each panel-field region box (`top`/`score`/`level`/`virus`/`speed`) also renders a small monospace debug line, fed by `getLastPanelDebug()` every frame (`updatePanelDebug()`, single-player only — versus never populates it): a confidently-matched digit/word shows its value and distance (`"5 (d=0)"`); a rejected one shows its `bestGuess` and distance in red (`.region-debug .miss`) so a field that's reading as blank/wrong shows *why* — genuinely no template close enough, or close but just outside `DEFAULT_MAX_DISTANCE` — instead of leaving the operator guessing whether the miscalibration is geometric (wrong crop) or photometric (compression/lighting pushing every distance up). Multi-digit fields (`top`/`score`/`level`/`virus`) join each digit's own entry with two spaces; `speed` (a single whole-word match) shows just one entry.
- Calibration's stored shape changed from a flat `{x,y,w,h}` to `{screen, regions}` — `loadCalibration()` in both `producer.js`/`harness.js` migrates an old flat value forward on load (treats it as `screen`, derives `regions` from it via the same quick-seed math) rather than requiring every existing operator to recalibrate from scratch.

**Speed pipeline integration**: DrMC's other main competitive format — two players each play their own independent single-player game, racing to clear a configured set of consecutive levels, best-of-3/5 races per match. Unlike Versus, the two games share no capture feed at all, so this genuinely needed the `MatchRoom`-equivalent Versus never did — but not a clone of Tetris's actual `MatchRoom`: no WebRTC camera peer relay, no curtain logos, no camera mirroring, no flexible N-player admin reassignment, since Speed is always exactly 2 fixed slots with no camera passthrough (the view renders full sprite bottles instead of compositing video). Two designs were weighed directly with the user before building this: a "two independent view connections, zero backend changes" version (each player's existing producer feeds a view opened with two secrets, with level-set config and reset buttons embedded in the OBS-visible page itself) versus a small dedicated room with a real, separate admin channel. The simpler design was the initial recommendation but was dropped once discussed further — it had no separation between "what the organizer controls" and "what's on stream" (controls reachable only via OBS's Interact mode on the *broadcast* page), no connection-status visibility, awkward slot swapping (edit the view URL, reload the OBS source), and — decisively, once best-of-N was raised — nowhere authoritative to keep `victories`/`bestof`/race-number state that survives an OBS browser-source crash/reload, since that's inherently server-side state. A losing player may also never finish their own run, so "who won this race" can never be auto-detected from frames the way nothing else server-side interprets Dr Mario frames either — a manual admin action either way, which a real admin channel accommodates naturally (mirrors how Tetris's own `MatchRoom.setVictories`/`setWinner` are already admin-driven, not inferred).
- `domains/DrMarioSpeedRoom.js` — a new, small `Room` subclass (2 fixed player slots, `bestof`/`levelSet`/`raceNumber`/`victories`/`headerText` state, one admin connection). Key simplification unavailable to Tetris's `MatchRoom`: since a Dr Mario producer connection only ever emits JSON frames (nothing server-side tracks game/score state the way Tetris's `Game`/`Producer` does), attaching a player to a slot doesn't require *that player's own connection* to "join" anything via a special URL the way Tetris's `u/<login>/producer1` convention does — the admin instead calls `setPlayer(slot, secret)`, the room resolves the user via the same `UserDAO.getUserBySecret()` lookup the view path already uses (confirmed to return the live in-memory `domains/User.js` instance, not a raw DB row, before relying on it), and subscribes to that user's *already-connected, completely unmodified* producer connection going forward. Players never see anything Speed-specific — they keep using `producer.html` exactly as it already works for an ordinary solo broadcast. `handleProducerMessage(slot, user, message)` is a parameterized version of `Room`'s own generic fallback (`['frame', slot, message]` instead of hardcoded `0`) — the same "tag with an index" convention Tetris's `MatchRoom.handleProducerMessage` already uses, minus the `Uint8Array` branch (Dr Mario producers never send binary frames). Race-winner detection (`recordRaceResult(winnerSlot)`) is manual, per the reasoning above; `resetPlayerRun(slot)` is the separate, non-race-ending manual override for aborting a bad/invalid attempt, both requested directly. A player's live connection status is pushed to the admin reactively (a listener on `DrMarioProducer`'s own `'close'` event, added/removed as a slot is attached/reattached), not just recomputed on the next admin action, so a dropped feed shows up without the admin having to do anything.

- `public/views/1p/drmario_speed_practice.html` — practicing a fixed level set solo (e.g. a 4-level set), reusing `SpeedRunTracker.js` directly against a single `RoundTracker`/`LiveMetrics` pair (no opponent, so none of `drmario_speed.html`'s cross-player elements — center-compare, crowns, bottom-bar, two-slot wiring — exist here). The level set is applied via `practice_admin.html`'s `speedPracticeSetLevelSet` command (see above) rather than an on-page control, but is still persisted to `localStorage` (as the full level array, one `drmario_speed_practice_level_set` key) so a reload of this OBS source remembers the last-applied set even if the admin page isn't currently connected to resend it — on load it seeds from that saved value, falling back to `[0,1,2,3]` if none exists yet. Otherwise reuses `drmario_speed.html`'s per-player column verbatim: top-strip (VIR/next-pill/SPD/TIME), 3-stripe bottle border, board-freeze/lookback machinery (`boardHistory`/`lastClearingBoard`/`freezeOnEarlierBoard()`), split list (per-level own duration, not cumulative), side stat box (PILLS/MIN, swapped for a drought/rush callout when active), and a freeze/dim recap overlay once `SpeedRunTracker` reaches `'complete'` — including the same guard against the real game continuing to fire `round_start` after the configured set is done (see `SpeedRunTracker.js`'s own header comment). The initial `applyLevelSet()` call (seeding the level set on page load) has to run *last*, after every function/state declaration below it in the module — an earlier version called it eagerly right after wiring the (now-removed) on-page config inputs, which synchronously reached into `resetDisplay()`/`renderSplitList()`/`roundEnded` and other `let` bindings declared later in the same module scope; a `let`/`const` binding is only usable after its own declaration actually executes ("temporal dead zone"), so that call threw before `connection.onMessage` was ever assigned, silently aborting the whole script and leaving the view permanently blank (reported live as "completely broken" — nothing rendered at all, not even a partial state).
- `public/producer/drmario/QualifyRunTracker.js` / `public/views/1p/drmario_qualify_practice.html` — practicing open-ended runs (no configured level set, starting wherever the practicer begins) with the specific stat DrMC Speed-tournament qualifying is scored on: level + remaining viruses at the 30-minute wall-clock mark. `QualifyRunTracker.js` mirrors `SpeedRunTracker.js`'s shape (`EventTarget`, `getSnapshot()`, driven by the same `RoundTracker` events) but two things differ on purpose:
  - **Topout ends the run.** Speed mode's same-level retry (the clock keeps ticking, `attemptsPerLevel` bumps) doesn't apply here — a real qualifying attempt is one continuous life, so `status` goes straight to `'ended'` on any non-`stage_clear` `round_end`, freezing `elapsedMs`; a further `round_start` (the real game not knowing the practice attempt "ended") is deliberately ignored until an explicit `reset()`, the same "stays frozen until explicit reset" pattern `drmario_speed.html`'s own board-freeze guard already established for the analogous real-game-keeps-going problem.
  - **No per-level split history is exposed** — per direct instruction, only `currentLevelElapsedMs`/`previousLevelElapsedMs` ("time this level"/"time last level"), not a full list (an open-ended run could span many levels). Internally it still keeps a `splits`-by-level checkpoint map exactly like `SpeedRunTracker.js` does, just never surfaces more than the last two entries — `round_end`'s own timing is used to record each checkpoint (not `round_start`/`round_level_confirmed`) specifically because `round_level_confirmed` can report a level's *start* well after the round itself actually began, whereas a level's *end* timing is always exact.
  - `checkQualifySnapshot()` is polled by the view on its own tick (same cadence as the live TIME box) rather than firing from a `RoundTracker` event, since crossing 30:00 wall-clock is not tied to any discrete OCR event — the instant elapsed time first reaches it, `{level, remainingViruses}` (current values at that moment, falling back to `virusTarget(level)` if the exact remaining count isn't known yet, same fallback precedent as `SpeedRunTracker`'s `totalVirusesRemaining`) is captured once and never overwritten afterward, exactly matching the direct requirement that continuing to play past 30 minutes must not disturb the captured score. Displayed as `${level}(${remainingViruses})` (e.g. `13(26)`) — the raw OCR level, matching every other on-screen level readout in this codebase (e.g. this same view's separate live `LVL` strip box); an earlier version added 1 to the level here based on a literal reading of an example in the original request ("14(32) for level 13"), but that was reported live as producing an incorrect score (level 13/26 viruses remaining displaying as "14(26)") and reverted. The view shows this in a gold-bordered `.qualify-pill` badge (blank `--` until captured, then frozen) and again in the freeze/dim recap once the run ends.
  - The live "This: mm:ss" / "Last: mm:ss" level-time box only updated on the tracker's own discrete `run_updated` events (round_ready/virus_cleared/round_end/...), not smoothly between them, because the view's own polling tick re-rendered from the *cached* snapshot object from the last such event instead of pulling a fresh one — that cached object's `currentLevelElapsedMs` is a plain number computed once at emission time, not a live getter, so it just sat frozen between events (reported live: "It seems to only update on virus clear"). Fixed by having the same tick that already recomputes the live TIME box (`Date.now() - runStartTime`) also reassign the view's cached snapshot to a fresh `qualifyTracker.getSnapshot()` call every 250ms, which every other renderer (`renderLevelTimes()`, the qualify badge, the freeze recap) reads from — `getSnapshot()` itself already recomputes every elapsed-time field off `Date.now()` on every call, so this was purely a "how often is it called" bug, not a tracker-logic one.

**Known gaps** (useful to know before assuming something is handled):
- A cell mid-match-clear is recognized (`type: 'clearing'`, a hollow-ring shape identical for both viruses and pills — see `templates.js` `CLEARING_TEMPLATE`), but only one visual frame of it has been captured, so a second blink state (if the game has one) isn't accounted for.
- Character sprites shown alongside the result boxes (Mario's victory/idle poses in `single_player_stage_clear.png`/`single_player_game_over.png`'s portrait box, Mario's in-bottle celebration pose in versus, the enemy virus's in-bottle topout pose) are **not** matched at all — the box alone already identifies the state unambiguously, so this was deliberately skipped as redundant/cosmetic. If a concrete use for the pose itself ever comes up, those captures already exist in `tests/fixtures/dr_mario/` to derive templates from.
- The blinking "START" prompt (visible in several of the result-state captures) isn't read.
- Only single-player and versus layouts exist (no other Dr. Mario modes have been captured).
- Versus-mode "garbage" pills entering the field are detected (`RoundTracker`'s `garbage_entered`), but tracking how far each one falls before coming to rest isn't built yet — there's no explicit "piece locked" signal in this OCR (single-player pieces have the same gap), so this would need its own design, not yet started.
- `RoundTracker`'s `piece_entered` can still double-count in one narrow, disclosed case: a piece that locks flush against a tall stack (never observed falling past row 1) *and* coincidentally shares its color pair with the very next real spawn (see the header comment at the top of `RoundTracker.js`, and the test documenting this exact scenario in `tests/DrMarioRoundTracker.test.js`).
- Single-player's "networked" head-to-head mode is now answered by Speed mode (`DrMarioSpeedRoom.js`/`SpeedRunTracker.js`/`drmario_speed.html`, see "Speed pipeline integration" above) — by design a differently-shaped, much lighter room than Tetris's actual `MatchRoom` (no camera passthrough, no flexible N-player reassignment, fixed 2 slots), not a gap anymore.
- No DB persistence for versus yet — no Dr-Mario-equivalent `Game.js`, `ScoreDAO`, or table; the server only relays frames, it doesn't record or score anything.
