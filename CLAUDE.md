# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

NESTrisChamps is a browser-based capture, broadcast, and rendering system for NES classic Tetris (and Das Trainer). A capture page ("producer") OCRs game state from video and streams it over WebSocket to a Node/Express server, which rebroadcasts it to one or more "renderer" pages (HTML+CSS+JS layouts meant to be used as OBS Browser Sources). Multiple players' streams can be combined into a live head-to-head competition UI with score differentials, tetris rate, pace, etc.

It's a plain ESM Node.js app (`"type": "module"` in package.json) with server-rendered EJS views for a few admin/settings pages, and hand-written vanilla JS for the actual capture/render frontends under `public/`. No frontend build step/bundler is used.

This fork (`drmariotrischamps`, forked from `nestrischamps/nestrischamps`) is adding equivalent OCR support for NES Dr. Mario. The OCR/event layer is self-contained under `public/producer/drmario/` (see below). Both versus and "non-networked" single-player are wired into the real capture/broadcast pipeline (routing, a domain object, a producer page, view layouts — see "Versus pipeline integration" below); "networked" head-to-head single-player (a `MatchRoom` equivalent) isn't, and there's no DB persistence for either mode yet.

## Commands

- `npm start` — runs the server (`node -r dotenv/config server.js`), reads config from `.env`
- `npm test` — runs Jest (`tests/*.test.js`), using native ESM (no transpilation: `transform: {}` in jest.config.js)
  - Run a single test file: `node --experimental-vm-modules node_modules/jest/bin/jest.js tests/ScoreService.test.js`
  - Run by name: add `-t "pattern"`
- `npm run lint` — runs both `lint-be` (ESLint on everything except `public/`) and `lint-fe` (ESLint on `public/`); backend and frontend have different global/env configs in `eslint.config.mjs`
- Prettier runs automatically on staged files via a Husky `pre-commit` hook (`pretty-quick --staged`) — formatting (tabs, single quotes, semicolons) is enforced at commit time, not just CI
- `npm run session` — utility script to set local session ids for dev/testing
- Local Postgres DB: apply `setup/db.sql`, plus any dated migration files in `setup/` in chronological order (e.g. `20250630.sql`) for schema changes not yet folded into `db.sql`
- Docker: `docker/build.sh` then `docker/run.sh` (docker-compose) spins up the app + a local Postgres container; see `docker/docker-compose.yml` for expected env vars

Required `.env` vars for local dev: `DATABASE_URL` (Postgres connection URI) and optionally `FF_SAVE_GAME_FRAMES=1` (persists captured game frames to `./games/` for replay/analysis). Full config schema (all env vars, including Twitch/Discord/Google OAuth, S3 game-frame storage, TURN server) lives in `modules/config.js` (uses `convict`) — that file is the source of truth for every env var the app reads.

## Architecture

### Two runtime halves

1. **Server** (`server.js`, `modules/`, `routes/`, `domains/`, `daos/`): Express app + a raw `ws` WebSocketServer sharing one HTTP(S) server. Express handles auth/OAuth, REST APIs, and EJS admin pages. The WebSocket server is the real-time backbone — game frames and control messages flow entirely over WS, not HTTP.
2. **Frontend** (`public/`, `views/`, `local_views/`): No build tooling — plain JS modules loaded directly by the browser and EJS-rendered HTML shells. `public/views/1p/` and `public/views/mp/` hold single-player and multiplayer *layouts* (each is a rendering skin: HTML/CSS/JS triplet meant to be dropped into OBS as a Browser Source at 720p). `modules/layouts.js` scans these directories at startup via `glob` to build the list of available layouts — adding a new layout is a filesystem convention, not a registration call.

### Connection routing is all in `routes/websocket.js`

Every WebSocket upgrade is manually dispatched by regex-matching `request.url` (there is no per-route handler abstraction like Express routes). Categories, in the order they're checked:
- `/ws/replay/<ids>` — replays stored games, no session needed
- `/ws/view/<layout>/<user_secret>` — a renderer/layout connecting as a *view*; resolves the owning user via `UserDAO.getUserBySecret` and fabricates a session
- `/ws/room/(u/<login>/)?(producer[12]?|emu)/<secret>` — a capture page connecting as a *producer*, optionally as a producer *into someone else's room* (competition/match mode) when the `u/<login>/` prefix is present
- `/ws/room/admin/<secret>` — the match-room admin control panel (blocked on public server unless routed through session-based auth)
- Anything else requires an established Express session (`request.session.user`)

Read this file first when touching anything connection-related; the in-memory domain objects below assume connections arrive already classified this way.

### Server-side domain model (`domains/`) — all in-memory, no per-connection persistence

- **`User`** (`domains/User.js`): one instance per logged-in user, kept alive in memory while it has active connections (auto-expires 30 min after last connection closes — see `checkScheduleDestroy`). Owns a `Producer`, a `PrivateRoom`, and a `MatchRoom`, and optionally joins another user's `MatchRoom` for head-to-head play. Also owns the optional Twitch chat client (`@twurple`) relaying chat/sub/raid events to connected clients.
- **`Producer`** (`domains/Producer.js`): wraps the capture-page WebSocket connection for a user. Parses incoming binary game frames vs JSON control messages, and owns the current `Game` instance (`modules/Game.js`), recreating it whenever a new game start is detected in the frame stream.
- **`Room`** (`domains/Room.js`, base class) / **`PrivateRoom`** / **`MatchRoom`**: fan out producer messages to connected view (renderer) connections. `MatchRoom` is the interesting one — it models up to `MAX_PLAYERS` (16) player slots, an admin control connection, auto-join logic, best-of-N/victories tracking, and a large command switch (`handleAdminMessage`) that is the actual protocol for the match-room admin UI.
- **`Connection`** (`modules/Connection.js`): thin `EventEmitter` wrapper around a raw `ws` socket — handles ping/pong keepalive, binary-vs-JSON message decoding (binary always means a game frame, decoded via `public/js/BinaryFrame.js`), and a "kick" sequence (send `_kick`, close, then hard-destroy after a delay so the client has time to see the message).

### Wire protocol

- **Control messages**: JSON arrays, `[command, ...args]`, sent as plain WS text frames. Most of the domain classes' message handling is just switching on `message[0]`.
- **Game frames**: a fixed 74-byte binary format (see `docs/schema.md` for the full byte layout) encoded/decoded by `public/js/BinaryFrame.js`, shared verbatim between server and browser code (this is why `jest.config.js` maps `/js/*` and `/views/*` to `public/js`/`public/views` — tests import the same frontend modules the browser loads).
- Score/stat computation from raw frames happens both client-side (live rendering, in `public/views/*.js`) and server-side (persisted scores via `modules/Game.js` → `daos/ScoreDAO.js` → Postgres `scores` table).

### Data layer

- `modules/db.js` exports a single shared `pg.Pool`, configured from `DATABASE_URL`.
- `daos/` (`UserDAO`, `ScoreDAO`) are the only modules that issue SQL directly — raw parameterized queries, no ORM.
- `domains/ScoreService.js` sits above `ScoreDAO` for query-option parsing/validation (allowed sort fields/dirs, page size clamped to `server.max_page`, competition-flag filtering) — extend validation there rather than in routes or the DAO.
- Schema evolves via dated one-off SQL files in `setup/` (e.g. `20250630.sql`) rather than a migration framework; `setup/db.sql` is the baseline.

### Config

All environment variables are declared and validated centrally in `modules/config.js` via `convict` (with a custom `boolean-string` format for env vars like `"true"`/`"1"`). `config.validate({ allowed: 'strict' })` runs at import time, so an unrecognized/undeclared env var will crash startup — always add new env vars to this schema rather than reading `process.env` directly elsewhere.

## Dr. Mario OCR (`public/producer/drmario/`)

A from-scratch OCR system for NES Dr. Mario, built the same way the Tetris OCR was originally derived: by pixel-analyzing real captures rather than guessing geometry/colors. Status: piece/panel identification is implemented and tested for both single-player and versus mode, and both are wired all the way into the real capture/broadcast pipeline (see "Versus pipeline integration" below — the name predates single-player joining it, but the same integration covers both). `tests/fixtures/dr_mario/*.png` are the real captures everything below was derived from and is tested against — add new ones there (with matching new Jest assertions) rather than hand-editing templates when new game states need covering.

**Key design difference from the Tetris OCR**: Tetris reads a field cell as one flat color sampled against a level palette (`../cpuTetrisOCR.js`'s `scanField()`), because a Tetris block always renders identically regardless of piece type. Dr. Mario can't do that — a virus and a pill segment can be the exact same color — so cells are identified by matching the actual NES tile *shape* (a small bank of hand-derived lit/unlit pixel templates), with color as a secondary signal. See `templates.js` for the full reasoning and how virus color/animation-frame and pill shape/color decompose differently (virus shape implies color; pill shape is color-independent, color needs separate sampling).

**Module map**:
- `shapeMatch.js` — shared pixel-sampling/template-matching primitives (`sampleRegion`, `trimToContent`, `matchBestTemplate`), used by every reader below. `sampleRegion`'s `invert` flag matters: sprites-on-black use bright-is-lit, but the score panel is black-text-on-light and needs the opposite — getting this backwards silently produces garbage matches (happened once; see git history on `PanelOCR.js`).
- `templates.js` / `digitTemplates.js` / `crownTemplates.js` — the actual shape banks (virus/pill tiles, the digit font + SPEED word, the versus-mode crown icon), each with real per-pixel provenance documented inline.
- `spriteBitmaps.js` / `CellRenderer.js` — real full-color NES sprite art for bottle rendering (see the `drmario_*_nes.html` layouts below), a separate concern from `templates.js`'s lit/unlit OCR-matching silhouettes even though both are derived from the same fixture captures. `spriteBitmaps.js` is generated data (a one-off extraction script, not committed, same precedent as `resultTemplates.js`): it ran the already-tested `BoardOCR.identifyCell()` classifier across several clean emulator fixtures and sampled the raw 8x8 RGB pixel grid of every cell it confidently identified, rather than hand-transcribing anything — see its own header comment for exactly which fixtures and the full provenance/gap accounting. 10 of the 15 (pill shape, color) combinations were found directly; blue left/right were *also* found directly but deliberately discarded and composed instead (see below), so 6 total are composed (documented per-entry) by taking a same-shape instance in a different color and substituting tones, since pill shape is confirmed color-independent (`templates.js`) and each pill color empirically turned out to use exactly 2 fill tones (its own `COLOR_PALETTE` base plus one shared "highlight" tone). The blue left/right discard: both were auto-found in `level00_frameA.png` (a *falling*-piece capture, unlike every other directly-sampled shape, which came from the landed `level00_pill_shapes.png`), and that particular instance rendered 1px lower than the canonical landed alignment — confirmed both by direct pixel inspection and live, after wiring this in, by the user (visibly offset from every other pill on screen) — exactly the per-instance jitter `templates.js`'s own header comment already warns about. Composing both halves from red's canonical pattern instead (not just the one side initially reported) keeps the pill's two halves aligned with *each other*, not only with the rest of the board. `CellRenderer.js` turns the bitmaps into cached offscreen canvases once at load and exposes `drawCell(ctx, x, y, size, cell, virusFrame)` (nearest-neighbor `drawImage` scaling, no per-pixel loop on redraw) and `currentVirusFrame(intervalMs = 125)` — a flat wall-clock toggle, deliberately *not* the `frame` value `identifyCell()`/`scanBoard()` already report per virus cell live. Using the real OCR-reported frame was considered and rejected directly with the user: it would risk visible flicker under real capture jitter (see `hasBottle`'s own jitter-tolerance fix) and would let different viruses in the same bottle drift out of sync with each other (each cell's own independent OCR read), whereas one shared clock keeps every virus blinking in unison — arguably more authentic to the real game (all its viruses animate on one shared beat) even though it isn't synced to any particular capture's real timing. Doubled twice from an initial 500ms guess (500 → 250 → 125ms), per direct feedback each time that it still read as too slow — none of these figures is a measured NES timing value (none exists in this codebase), purely cosmetic.
- `BoardOCR.js` — `identifyCell()`/`scanBoard()` (the 8x16 bottle grid) and `identifyNextPill()` (the preview pill, positioned above Mario's head in single-player or in each bottle's neck in versus — a fixed screen position, not a grid cell). Both take a `field`/`position` option so the same code drives either single-player's one bottle or versus mode's two.
- `PanelOCR.js` — `readNumber()` (TOP/SCORE/LEVEL/VIRUS digit sequences) and `readSpeed()` (LOW/MED/HI, matched as a whole word, not per-letter).
- `CrownOCR.js` — versus-mode round-wins tracker; reports a win *count* per player rather than assuming which grid cell fills first (only one example was ever observed).
- `resultTemplates.js` / `ResultOCR.js` — `readResult(image, field)` reads a bottle's round/match state: `'playing'` | `'stage_clear'` | `'game_over'` | (versus only) `'topout'`. STAGE CLEAR and GAME OVER are the same box design (red border, yellow fill, vertically centered on a fixed point regardless of text length) anchored to each bottle's own position, so one template pair and one bottle-relative sample region covers single-player and both versus bottles; topout is a separate, smaller, lower box sampled at its own offset, since it doesn't replace the bottle's contents (the overflowed pieces stay visible above it) the way the other two do. `resultTemplates.js` is generated by a one-off extraction script, not hand-transcribed — see its top comment before hand-editing it (a manual first attempt silently dropped rows and produced garbage matches). `readResult` assumes a bottle is actually present — see `ScreenOCR.js` below for the screens where that's not true.
- `ScreenOCR.js` — `hasBottle(image, field)`, answering "is there a bottle on screen at all," distinct from (and a prerequisite for trusting) everything else above. Dr. Mario has several screens with no bottle whatsoever — pause (the screen goes black except white "PAUSE" text), the title screen, and the 1P/2P game-setup menu — and every other reader here just produces misleading output if pointed at one instead (an all-black pause screen reads as an empty board; `ResultOCR`'s `'playing'` default makes a title/menu screen look like an ordinary in-progress round). Rather than building a detector per screen, it checks for the cyan bottle-wall color at two fixed points relative to `field`'s own origin — present on every real bottle, absent on all three non-gameplay screens. `isTitleScreen(image)` narrows further, telling the title screen apart from pause/menu specifically (a whole-screen check, no `field`) — needed because a player can soft-reset the console mid-round via a controller command, jumping straight to the title screen with none of the usual `'game_over'`/`'topout'` result on the way (see `RoundTracker.js`). Keys on the title screen's decorative checkerboard, which alternates between two greens — the darker shade alone isn't unique (some ordinary gameplay levels' own checkerboard uses it too), but the brighter one never appears anywhere else on hand.
- `constants.js` — all geometry (`FIELD`, `NEXT_PILL`, `VERSUS.*`), the `COLOR_PALETTE`, and `LAYOUT`/`CONFIGS`/`REFERENCE_LOCATIONS`(`_VERSUS`) tying it together. Every coordinate here was measured off a real capture, not estimated — see the git history for the actual pixel-dump methodology if new geometry ever needs deriving (e.g. for a layout variant).
- `DrMarioOCR.js` — the DOM-facing live-video counterpart to the above (mirrors `../TetrisOCR.js`'s shape: `EventTarget`, `processVideoFrame({video, videoFrame})`, a `'frame'` event), simpler than Tetris's because shape-matching needs no per-task packing canvas. Calibration is currently just one axis-aligned crop rectangle (video pixels → the 256x224 reference frame) — no skew/rotation correction yet. Every scanned bottle is gated through `ScreenOCR.hasBottle` first: when it's false the returned per-bottle shape has `hasBottle: false` and every other field (`result`/`board`/`nextPill`/`level`/`virus`/`speed`, plus `top`/`score` in single-player) null, rather than running the rest of the OCR pipeline against a screen it wasn't built to read. `isTitleScreen` (from `ScreenOCR.isTitleScreen`, computed once per frame against the whole image) is attached to every per-bottle shape the same way `hasBottle` is, even though it's a whole-screen fact rather than a per-bottle one — `RoundTracker` only ever sees one bottle's frames, so it needs the flag on its own frame object to act on it.
- `RoundTracker.js` — the per-bottle state machine (mirrors `../GameTracker.js`'s role) that turns a *sequence* of frames into `round_start`/`round_level_confirmed`/`round_ready`/`round_end`/`piece_entered`/`garbage_entered`/`virus_cleared` events. One instance per bottle (versus mode uses two). Unlike GameTracker it doesn't need a score/lines heuristic to find round boundaries — `ResultOCR`'s state already gives that directly — and it tracks virus count as two-phase (up during population toward `4*(level+1)`, capped at 84 for level 21+, then down) rather than monotonic. `piece_entered` fires when a player-controlled piece spawns, detected by position and scoped specifically to the fixed pair of middle columns a real spawn always uses (confirmed report), *not* the whole top row — an earlier version watched the whole row and misread the player shifting/rotating a piece still sitting in row 0 as repeated new spawns. Scoping to the spawn pair alone still double-counted real player input (a piece slid off the spawn pair and back, or rotated 180° in place, both leave then re-fill it without a real spawn happening — confirmed live), so re-arming detection now requires positive evidence the previously-reported piece actually left play: either the next-pill preview changing (confirmed via real captures — see `BoardOCR.identifyNextPill`'s doc comment — to hold constant while the current piece is in play; blind spot: two real consecutive pieces can coincidentally share a color pair, since there are only 3 colors) or new pill content appearing one row below spawn or deeper (a rotation alone can never reach that far — confirmed report that the second cell of a vertical pill goes *up*, off the top of the bottle, not down; blind spot: a piece that locks against a tall stack before ever falling that far). The two blind spots are unrelated, so either signal alone is enough to disambiguate; only their conjunction still double-counts (documented and tested, not fixed). `piece_entered` also requires both spawn cells to be the paired `'left'`/`'right'` shapes specifically (not just any pill), so a garbage half (see below) landing on a spawn column can never be misread as part of a real spawn. `garbage_entered` (versus only) fires when one or more loose `'single'`-shaped halves (see `templates.js`'s `PILL_SHAPE_TEMPLATES`) appear on the top row — confirmed report: 2/3/4 can enter at once, always with at least a column of gap between them, landing in any column including the spawn pair — batched into one event per frame per column that was genuinely empty the frame before; a `'single'` overwriting an already-occupied column is deliberately not tracked (confirmed report that garbage does this, but not a case worth the complexity of reporting precisely). Detection stays disarmed at the start of each round until a frame where the *entire* top row reads empty has actually been observed (`#topRowConfirmedEmpty`) — `#topRowEmpty` otherwise resets to an optimistic all-empty default on every `#startRound()` with no real prior-frame observation behind it, and a half-pill orphaned by a match clear late in the *previous* round can still be visually sitting in the top row for the first frame or two of the next one, before the screen actually clears it; without this guard that leftover cell reads as a same-frame empty-to-single transition and fires a false `garbage_entered` before the player's first piece has even spawned (reported live). Each cell also carries `restRows` — how many rows it'll fall before resting, inclusive of the spawn row, computed once at arrival from the board already in hand rather than tracked live as it actually falls (garbage falls at a constant rate regardless of game speed, so both approaches land on the same number) — plus `maxRestRows` on the event as a whole (the farthest-falling cell in the wave); purely geometric, exists for `LiveMetrics.js`'s SALT stat, not used by round-lifecycle logic itself. `virus_cleared` fires whenever the tracked virus count drops during ordinary play (population increases don't count, handled separately), with the delta so a poll that misses an intermediate frame still attributes the right total — also purely for `LiveMetrics.js`'s benefit. A frame with `hasBottle: false` (see `ScreenOCR.js`) is a complete no-op *unless* `isTitleScreen` is also true and a round was actually in progress — a soft reset via a controller command jumps straight to the title screen mid-round with no `result` transition to detect otherwise, which would leave a round stuck open forever without this; ordinary pause/menu screens still don't look like a round boundary, and a title/menu screen in front of the capture still can't bootstrap a bogus `round_start`. Versus mode's round boundary is shared between both bottles — one player's win/loss ends the round for both, even though the other bottle's own `result` reading can keep showing `'playing'` (reported live) — which a single instance watching only its own bottle can't notice on its own, so `endRound(outcome)` lets the consumer running both players' trackers (see `harness.js`'s versus wiring) propagate one tracker's `round_end` onto the other; it's a no-op if that tracker already ended its own round, so cross-wiring both directions can't double-fire or loop. The same desync happens in reverse at the *start* of the next round (reported live): the unaffected bottle's own board/panel data can already reflect the new round before the affected bottle's own overlay has cleared (that one's `result` only reads `'playing'` again once it does), so letting the unaffected tracker self-detect its own round_start would report the round starting a real amount of time before it actually does for the affected player. A tracker that ended via `endRound()` now waits instead of self-detecting; `syncRoundStart({roundId})` (same versus wiring, on `round_start` this time) relays the affected tracker's own later, real round_start onto it, also a no-op unless that tracker is actually waiting for one. Deliberately takes only `roundId`, never `level` — each player's level is set independently (reported live: 1P on level 7 while 2P was on level 0), so borrowing it from the other tracker was a real regression caught live (round_ready firing far too early off the wrong target); the synced round starts with `level: null` and lets it self-heal from this bottle's own frames exactly like an ordinary unreadable-at-round_start case. Pure state-machine logic, no OCR/pixels involved — tested against hand-built frame sequences, not image fixtures; this particular heuristic hasn't been validated against real captured timing data, only against live-harness repros.
- `LiveMetrics.js` — a live-stats layer built on top of one `RoundTracker`'s events, mirroring how Tetris's `../views/BaseGame.js` (simple running counters off discrete events) sits under `../views/Player.js`/view-layer closures (bespoke streaks) rather than any of it living in the frame-decoding layer itself — researched that split deliberately before designing this. Named `LiveMetrics`, not the more obvious "StatsTracker" — that name shipped first and was found live to trip ad/tracker-blocker extensions (`ERR_BLOCKED_BY_CLIENT`) that filter requests matching generic "stats"/"tracker" analytics-script patterns, silently killing the whole page's script execution (the sibling `RoundTracker.js`, no "stats" in its name, loaded fine) — renamed rather than asking every viewer to allowlist the domain. One instance per bottle, `EventTarget`-based like `RoundTracker`, dispatches one `stats_updated` event (a full snapshot via `getSnapshot()`) on any change. Self-derived from its own bottle: `piecesPerMinute`/`virusClearsPerMinute` (wall-clock `Date.now()`, no prior time-basis convention existed anywhere in this codebase to match — see `../views/BaseGame.js`'s `duration`/`modules/Game.js`'s `duration` for the two unrelated, non-rate conventions that do exist), `colorDroughts` (per-color pieces-since-last-seen, directly mirrors `BaseGame.js`'s per-piece-type drought), and `rushStreak`/`maxRushStreak`/`isRushing` (4+ *exact same piece including orientation* in a row — order matters, e.g. blue-red/blue-red/red-blue/blue-red is not a rush since the third piece's swapped orientation breaks it, confirmed report). Externally reported (versus only): `recordGarbageSent({cellCount, maxRestRows})` — not wired to its own bottle's events at all, since "garbage sent" is inherently about the *other* bottle's `garbage_entered`; the consumer calls it on player A's tracker when player B's `garbage_entered` fires, the same cross-player-coordination-lives-in-the-consumer split `RoundTracker`'s `endRound()`/`syncRoundStart()` already established — feeds `garbageWavesSent` (a plain running total; the versus view displays this and its derived rate as "combos", the term the user actually uses for a wave of garbage), `garbageWavesSentPerMinute`, `averageGarbageWaveSize` (labeled "CUR" — Combo Utilization Rate — in the view; that name and the display threshold below are both view-layer choices, not something `LiveMetrics` itself encodes), and `saltSeconds` (cumulative, `maxRestRows * 0.25`s per call, since garbage falls at a constant rate regardless of game speed — briefly changed to 0.2667 on a correction from the user that turned out to be wrong and reverted back to the original 0.25 figure). The per-row constant is also exported (`SALT_SECONDS_PER_ROW`) so a view can time a display-only "count up" animation against the exact same figure the accumulation itself uses, rather than duplicating it — see `drmario_versus.html` below. Single-player's own round boundary fires on every *level*, not just when a playthrough ends (a `round_end` with `outcome: 'stage_clear'` just advances to a harder level, same playthrough) — resetting rate/streak/drought stats on every one of those would make them jump every time a level clears, so a `carryAcrossLevels` constructor option (single-player only, off by default) makes `LiveMetrics` listen to `round_end` too and only reset on the *next* `round_start` if the previous round didn't end in `'stage_clear'`; versus keeps the simpler always-reset-per-round default, since it has no "advance to a harder level, same run" concept today (match-wide stats across a best of 3/5 are a possible later expansion, not this). A public `resetRun()` is also exposed as a manual override regardless of automatic detection, wired to a button in both view layouts.
- `InternalSpeed.js` — `calculateInternalSpeed(speedName, piecesEntered)`, a pure/stateless function decoding the game's real internal fall-speed from the displayed LOW/MED/HI value, which isn't the actual speed the game runs at. Per the user's own account of the mechanic: a base value per displayed speed (LOW 15, MED 25, HI 31) increases by 1 as the 9th pill enters a level (i.e. once the 8th has locked), then by 1 again every 10 pills after that, up to a cap of 49 increases (HI caps at 80, MED at 74; LOW's cap of 64 follows the same +49 pattern but wasn't independently confirmed). `piecesEntered` is a running count of `RoundTracker`'s `piece_entered` events since the current round started, tracked inline in each view (not in `RoundTracker`/`LiveMetrics` itself — this is a self-contained, easily unit-tested calculation, not round-lifecycle logic or a rate/streak stat) and reset unconditionally on every `round_start`, regardless of single-player's `carryAcrossLevels` — the real game's own speed ramp genuinely restarts every level, it isn't a "run" concept the way pieces/min is. All 4 view layouts (`drmario_single(_nes).html`, `drmario_versus(_nes).html`) now display this computed number in place of the raw LOW/MED/HI text.
- `harness.html` / `harness.js` — standalone page (not part of `ntc-capture`/`CaptureDriver`/the real broadcast flow) for visually testing the above against a real camera or screen/window capture, including a live `RoundTracker` event log. Open `/producer/drmario/harness.html` directly.

**Versus pipeline integration**: Dr. Mario versus is single-system — one capture feed already shows both bottles (that's exactly `DrMarioOCR`'s versus frame shape) — so unlike Tetris's head-to-head mode, it needed no `MatchRoom` equivalent, just a private-room-style path parallel to Tetris's. Wire format is plain JSON (the `DrMarioOCR` frame object itself), not a new packed binary format — `domains/Room.js`'s `handleProducerMessage()` already had a generic fallback (any message that's neither `Uint8Array` nor an `Array` gets wrapped `['frame', 0, message]` and broadcast), and both the client (`public/js/connection.js`) and server (`modules/Connection.js`) `Connection` classes already `JSON.stringify`/`JSON.parse` generically — so the entire transport/relay layer needed no new code at all, just new things to plug into it:
- `domains/DrMarioProducer.js` — mirrors `Producer.js`'s connection lifecycle with no Tetris `Game` construction; this phase doesn't interpret frames server-side or persist anything, it only relays.
- `domains/User.js` — new `drmario_producer`/`drmario_private_room` fields (the latter is a plain, unmodified `PrivateRoom`) alongside the existing Tetris ones, with matching `getDrMarioProducer()`/`getDrMarioPrivateRoom()`/`setDrMarioProducerConnection()`/`_handleDrMarioProducerMessage()`.

The SALT figure in `drmario_versus.html`'s combo line "counts up" visually rather than jumping straight to the new cumulative total on each `garbage_entered` wave — a `requestAnimationFrame` loop (`startSaltCountUp`/`tickSalt`) interpolates the displayed number from wherever it currently sits to the (already-authoritative, computed synchronously by `LiveMetrics`) new total, over the wave's real fall duration (`maxRestRows * SALT_SECONDS_PER_ROW`, imported from `LiveMetrics.js` rather than duplicated). Always animates from its current displayed value rather than the pre-wave total, so an overlapping second wave just re-aims at the new (higher) target instead of stacking animations; a `LiveMetrics` reset mid-animation (round_start/`resetRun`) is detected (`saltSeconds` dropping below the in-flight target) and snaps the display straight to the authoritative value rather than keep counting toward a now-stale one.

The synced side's own `round_end` reports a synthetic `opponent_<outcome>` string (from the cross-wiring), not a real `ResultOCR` state this bottle's own OCR read directly. `formatOutcome()` treats `game_over` specially: it's genuinely shared (both bottles really do end up on the same match/session-ending screen), so both sides show the same word — an earlier version showed a generic "ROUND OVER" for the synced side instead, which read as a mismatch once both bottles' text was visible side by side (reported live: one side "GAME OVER", the other "ROUND OVER"). `topout`/`stage_clear` are different — genuinely per-bottle outcomes, not shared ones, so labeling the synced side with either would be actively wrong (not just vague), and per direct request `formatOutcome()` now returns an empty string for the synced side there instead — the freeze/dim + stats recap still shows (`updateFreezeOverlay` doesn't gate on the outcome text at all), just without a specific, inaccurate outcome claim. A further wrinkle, also confirmed live: between the *match*-deciding round's own end screen and the shared match-level GAME OVER screen, there's a brief spurious transition where the OCR reads the bottle as `'playing'` again (almost certainly a screen-wipe frame misread as an empty board), which fired a bogus `round_start`, reset `LiveMetrics`' stats, and dropped the freeze overlay right when it mattered most. Fixed with a `matchOver` flag, set the instant either player's crown count (`data.crowns.playerX.wins`, already available on every frame) reaches 3 — once set, both players' `round_start` listeners no-op (can no longer un-freeze `roundEnded`) and `renderStats` stops updating `latestSnapshot`, so nothing displayed can drift while the GAME OVER screen is up; crown count, not the round-boundary machinery, is the one signal here that's unambiguous about when the *match* (not just the round) has ended. That lock was originally permanent, which turned out to be overly aggressive (reported live): after GAME OVER the game eventually returns to a menu to set up another match, and with no way to detect that the frozen overlay stayed stuck until the whole page was reloaded. Crown count is the fix here too, via `checkMatchState()` (renamed from `checkMatchOver()` once it grew this second job) and `resetMatchState()`: once a fresh match begins — or the crown grid simply isn't on screen at all right now (menu/title, nothing crown-shaped to read) — both crowns read back at 0, which the previous match's "one side has 3" state could never do on its own, so seeing 0-0 while `matchOver` is set is treated as an unambiguous signal to reset every player-keyed piece of state (`roundEnded`, `lastOutcome`, `latestSnapshot`, `boardHistory`, `lastClearingBoard`) and re-run `updateFreezeOverlay` immediately, rather than leaving the stale frozen overlay up through the whole menu-browsing period. `resetMatchState()` also explicitly clears both board canvases (`renderBoard(canvas, null)`, reusing its own existing null-board clear path) — un-freezing alone wasn't enough on its own, since `renderBoard()` is never called with a real board while on a menu screen (`hasBottle: false`, `board: null`), so the previous match's last frame would otherwise just sit there undimmed for the whole menu-browsing period instead of going blank (requested directly). One more wrinkle, also confirmed live with a screenshot: the character/virus celebration pose that plays right as a round ends isn't OCR-matched at all (see this file's own "Known gaps" section below), and can already be on screen — obscuring real cells near the top of the bottle — for a few frames *before* `result` actually leaves `'playing'`, so freezing on literally the last frame drawn risked freezing on that already-obscured one. Fixed with a small `boardHistory` (fed alongside the ordinary live `renderBoard()` calls, reset on each `round_start`): `round_end` now calls `freezeOnEarlierBoard()`, which re-renders the canvas from an earlier remembered frame rather than leaving whatever was already drawn. The obstruction turned out not to last the same number of frames for every outcome (reported live over a couple of rounds of live tuning): a single fixed lookback either left `stage_clear` still showing grey "unknown" cells or, once increased enough to fix that, cropped the very pill that caused a `topout` out of frame (`topout`'s own result box is small and doesn't cover the board the way `stage_clear`'s/`game_over`'s do — see `ResultOCR.js`'s own docs — so it needs far less correcting for). `BOARD_LOOKBACK_FRAMES` is a plain per-outcome lookup table (`topout: 1`, `game_over: 4`, with `DEFAULT_BOARD_LOOKBACK_FRAMES` as the fallback for anything else) rather than one constant for every outcome — retuned live more than once as reports came in (`topout` briefly went to `0`, which then showed grey cells again; `1` is where it landed) — and `BOARD_HISTORY_SIZE` is derived from its largest value so the buffer is always exactly big enough. `stage_clear` doesn't use the lookback table at all: an initial attempt keyed off `RoundTracker`'s `virus_cleared` event (capturing the board the instant the tracked virus count hit 0) landed a frame *before* the on-screen clear animation, not during it, when what was actually wanted was the "O" ring animation itself being visible. `templates.js`'s `'clearing'` cell type (a hollow ring, replacing whatever virus/pill was there) *is* that animation, read directly off the board by `identifyCell()` — no separate signal to time against needed, so `lastClearingBoard` just remembers the last frame (while the round is still live) that actually had one, updated inside `recordBoardHistory()` alongside the ordinary lookback buffer. Nothing else can happen in the bottle after the stage-clearing match but the round ending, so the last such frame recorded is guaranteed to be *that* match, not an earlier ordinary one from mid-round play. `freezeOnEarlierBoard()` prefers it whenever available; it won't be for the synced side unless that bottle also happened to clear its own viruses (a per-bottle signal, not a shared one), in which case the lookback table remains the fallback there.

  "Has a clearing cell" alone still wasn't enough (diagnosed live): the STAGE CLEAR box draws in from the *bottom* of the bottle upward, so a single frame can show real "O" rings further up while cells nearer the bottom are already covered and reading as `'unknown'` — the exact frame with the rings we want can already be partway corrupted by the same box that triggered `stage_clear` in the first place. `CLEARING_MAX_UNKNOWN_CELLS` (3) now also requires the candidate frame to be mostly free of `'unknown'` cells, not just contain a ring somewhere — the Mario victory pose that eventually appears as the box keeps growing covers (at least) 4 cells along the bottom row on its own, so staying strictly below that leaves a little leeway for incidental noise while still landing on a frame from before that particular artifact.

  Freezing correctly still didn't *stay* frozen, in two different ways (both reported live): after `game_over`, and less obviously after a match-ending `stage_clear`/`topout`, the displayed board would visibly change again some time after the initial freeze. Root cause: the spurious `'playing'` misread `matchOver`'s own comment already documents can happen *before* crown count has caught up to reflect the match actually being over, since the OCR's crown-grid read and each bottle's own result-screen read don't update in lockstep — so a bogus `round_start` could still slip through and un-freeze things in that gap, regardless of which specific outcome ended the match. Rather than special-case per outcome, `ROUND_END_GRACE_MS` (1500ms) blocks `round_start` unconditionally for a short window after *any* `round_end`, tracked per player in `roundEndedAt`; a real next round — match-ending or not — always takes noticeably longer than that to actually begin, so this only ever filters the brief transition-frame glitch, never a legitimate round start. `isFreezeLocked(playerKey)` combines this with the existing `matchOver` check and is now what both `round_start` listeners and `renderStats()` gate on (previously just `matchOver`) — `renderStats()` needed the same guard because `LiveMetrics` resets its own counters on `round_start` regardless of what this view does with `roundEnded`, so `latestSnapshot` could still have drifted even with the board itself correctly held in place.

- No DB persistence in this phase — no Dr-Mario-equivalent `Game.js`/`ScoreDAO`, no new table.
- Single-player integration required zero changes to `domains/DrMarioProducer.js`, `domains/User.js`, or `routes/websocket.js` — the server only relays JSON frames, it never inspects `layout`, so the exact same producer connection and private room already serve both modes; only the producer/view *pages* needed to grow a single-player path.

**Known gaps** (useful to know before assuming something is handled):
- A cell mid-match-clear is recognized (`type: 'clearing'`, a hollow-ring shape identical for both viruses and pills — see `templates.js` `CLEARING_TEMPLATE`), but only one visual frame of it has been captured, so a second blink state (if the game has one) isn't accounted for.
- Character sprites shown alongside the result boxes (Mario's victory/idle poses in `single_player_stage_clear.png`/`single_player_game_over.png`'s portrait box, Mario's in-bottle celebration pose in versus, the enemy virus's in-bottle topout pose) are **not** matched at all — the box alone already identifies the state unambiguously, so this was deliberately skipped as redundant/cosmetic. If a concrete use for the pose itself ever comes up, those captures already exist in `tests/fixtures/dr_mario/` to derive templates from.
- The blinking "START" prompt (visible in several of the result-state captures) isn't read.
- Only single-player and versus layouts exist (no other Dr. Mario modes have been captured).
- Versus-mode "garbage" pills entering the field are detected (`RoundTracker`'s `garbage_entered`), but tracking how far each one falls before coming to rest isn't built yet — there's no explicit "piece locked" signal in this OCR (single-player pieces have the same gap), so this would need its own design, not yet started.
- `RoundTracker`'s `piece_entered` can still double-count in one narrow, disclosed case: a piece that locks flush against a tall stack (never observed falling past row 1) *and* coincidentally shares its color pair with the very next real spawn (see the header comment at the top of `RoundTracker.js`, and the test documenting this exact scenario in `tests/DrMarioRoundTracker.test.js`).
- Single-player's "networked" head-to-head mode (a `MatchRoom` equivalent on the single-player board, racing to clear levels — mirrors Tetris's actual `MatchRoom` usage) isn't built — only the "non-networked" solo-stream path is wired up so far.
- No DB persistence for versus yet — no Dr-Mario-equivalent `Game.js`, `ScoreDAO`, or table; the server only relays frames, it doesn't record or score anything.
